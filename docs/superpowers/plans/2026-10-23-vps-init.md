# VPS Initialization Script Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One script that turns a fresh Debian 13 VPS into a running AcroWorldTour host (prod + training), ending after the first successful deploy.

**Architecture:** `deploy/init-vps.sh` (bash, run as root) is a sequence of idempotent steps. Every input comes from an environment variable or, if unset, an interactive prompt (secrets hidden). Repository files it needs (`deploy/agent.sh`, `deploy/deploy.sh`, systemd units, env examples) are fetched from the public repository at the deploy branch; `compose.yaml` and `Caddyfile` come from the image (installed by the agent). The first deploy is the agent's first run; if the S3 bucket holds a Litestream replica, the container restores it at start (existing entrypoint behaviour), otherwise the database starts empty and the script points to `docs/ops.md` §4.

**Tech Stack:** bash, apt, Docker Engine + Compose plugin (Docker's apt repo), nftables, OpenSSH, fail2ban, unattended-upgrades, systemd.

**Spec:** Agreed in conversation on 2026-10-23 (owner): fresh Debian 13 → everything installed and configured; inputs from env vars or prompts; stop when the server is ready and the first deploy is done; restore the database from S3 when present, else empty database + pointer to the docs. Existing procedure to automate: `docs/ops.md` §1–§3 and §5 (pull agent).

## Global Constraints

- Debian 13 (trixie) only: check `/etc/os-release` (`ID=debian`, `VERSION_ID=13`), refuse otherwise (override `AWT_INIT_ALLOW_OS=1` for tests). Must run as root.
- Idempotent: every step checks before acting; re-running on a configured host changes nothing and succeeds. Never overwrite an existing secret/env file value without `AWT_INIT_FORCE=1`; fill only missing keys.
- Inputs: env var first, else prompt (`read -r`; secrets with `read -rs`); no prompt when stdin is not a TTY → fail listing the missing variables (non-interactive mode). Validate formats (hosts, port 1024–65535, SSH public key, base64 32-byte keys, PEM certificate/key pair matching).
- Inputs list (names fixed): `AWT_ADMIN_USER`, `AWT_ADMIN_SSH_KEY` (public key line), `AWT_SSH_PORT` (default 2222), `AWT_PROD_HOST`, `AWT_TRAINING_HOST`, `AWT_IMAGE` (default `ghcr.io/fatpat/awt`), `AWT_CHANNEL` (default `rewrite-go`), `AWT_REPO_RAW` (default `https://raw.githubusercontent.com/fatpat/acroworldtour.com/$AWT_CHANNEL`), per environment `PROD_`/`TRAINING_` prefixed: `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `MFA_KEY`, `CLOUDFLARE_ZONE_ID` + `CLOUDFLARE_TOKEN` (optional pair), and `AWT_TLS_CERT_FILE` / `AWT_TLS_KEY_FILE` (paths) or pasted PEM.
- MFA key: if the environment's S3 bucket already contains a Litestream replica (check with `litestream`'s or an S3 listing via a one-shot container using the app image: `docker run --rm --entrypoint litestream <image> snapshots -config /etc/litestream.yml ...` or an equivalent `ls` of the replica path), the key is REQUIRED (prompt, no generation, warn why); otherwise generate with `openssl rand -base64 32` when not provided.
- Secrets never printed or logged; the final summary masks them (`****` + last 4). Files with secrets mode 600, owner `deploy`.
- SSH hardening must not lock the operator out: install the admin key and validate `sshd -t` before reload; keep the current session; print the new port and a "test a new SSH session before closing this one" warning; open the new port in nftables before restricting.
- Firewall (nftables, persistent `/etc/nftables.conf` include `/etc/nftables.d/awt.nft`): inbound allow established, loopback, ICMP, SSH port from anywhere, 80/443 (tcp, and udp 443) from Cloudflare ranges only (fetched from `https://www.cloudflare.com/ips-v4` and `ips-v6` at run time, with a pinned fallback list in the script); default drop. Docker: published ports bypass the input chain — filter in a `DOCKER-USER`-equivalent nftables chain (forward hook) or set Docker `"iptables": true` and add the Cloudflare-only rule to `DOCKER-USER`; choose and document one approach that really blocks non-Cloudflare traffic to 80/443.
- Reuse existing repo artefacts (agent, deploy.sh, units, env examples, ops.md procedures); no second copy of their content in the script.
- No changes under `legacy/`. CLAUDE.md applies.

## Review Focus

1. **Re-run on an already configured VPS**: no changes, no prompts for values already stored, exit 0. Test: run twice in the test container; second run reports "already done" for each step and file checksums are unchanged.
2. **Operator would be locked out** (bad SSH key, sshd config error): script refuses to reload sshd and exits with a clear message; current SSH config left in place. Test: invalid `AWT_ADMIN_SSH_KEY` → refused before touching sshd.
3. **Non-interactive run with missing values**: exits non-zero listing every missing variable at once (not one per run). Test.
4. **S3 has a replica but no MFA key given**: refuses to generate one and asks (or fails non-interactive with an explanation). Test with a fake replica check.
5. **First deploy fails** (agent exit non-zero): script prints the agent's journal tail and the next steps, exits non-zero, everything else stays installed so a re-run resumes. Test with a stubbed agent.
